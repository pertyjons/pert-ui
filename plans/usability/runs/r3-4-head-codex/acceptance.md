## Items

### 1. One test per listed behavior, all passing — **met**

Each of the seven README behaviors has a dedicated test in
`work/bookmarks/tests/ui.rs`. All mount the unchanged app with
`bookmarks::build` into a headless `Runtime`, act only through `Driver`
(`click` = simulated pointer press/release at the target's bounds;
`replace_text` = focus + SelectAll + `Runtime::text_input`/Backspace;
`chord` = synthesized modifier + key events via `command_key_input`;
`clear_focus` = host deactivation), and assert through `Driver::semantics`
(label `name`, `SemanticValue::Text`, role) and `Driver::address_children`
(ordered `Each` row keys). No application function other than the public
`build` is called. Verified in the vendored runtime source
(`pert-ui-runtime-0.3.88/src/testing.rs:802, 1002, 1130, 1232`).

| README behavior | Tester test (`tests/ui.rs`) | What it establishes |
|---|---|---|
| 1 Add | `add_appends_and_trims_name` (l.84) | two adds (https and http) append rows `3`,`4` at the end; names trimmed; URL kept; originals intact |
| 2 Refused add | `refused_add_preserves_fields_and_success_clears_error` (l.101) | empty/blank names and ftp/empty URLs refused; correct message incl. name-first precedence (`""`, `"invalid"`); both fields keep text; no row added; next success clears the label (`name == None`) |
| 3 Fields cleared | `successful_add_clears_both_fields` (l.126) | both fields' text values empty after success |
| 4 List | `list_shows_rows_and_remove_deletes_only_its_bookmark` (l.136) | each row's name/url labels and a `Button` role "Remove"; removing row `1` with a same-name duplicate present removes only that id |
| 5 Filter | `filter_matches_name_substrings_ignoring_case_and_spaces` (l.160) | case-insensitive substring, surrounding spaces ignored, URL text not matched, blank/empty shows all |
| 6 Status | `status_counts_visible_and_total_bookmarks` (l.178) | `N bookmarks` incl. `1 bookmarks`/`0 bookmarks`; `N of M bookmarks` while filtering, including after Remove under a filter |
| 7 Clear filter | `clear_filter_keyboard_command_works_wherever_focus_is` (l.199) | `KeyChord::primary('l')` chord empties the filter from five starting points |

Gap in the tester's evidence and the verifier's supplement: test 7 never
checks where focus is before the chord. It reaches the Add button by clicking it,
which also triggers a refused add as a side effect. The verifier's
`work/bookmarks/tests/acceptance.rs` adds:

- `acceptance_ctrl_l_clears_filter_from_inspected_focus`: types the filter
  character by character (`type_text`), moves focus to the filter, Name,
  URL, Add and a row's Remove button **by Tab key only**, or clears focus.
  It asserts `Runtime::focused()` equals the intended widget before every
  Ctrl+L. It then asserts that the filter is empty, all rows are shown, the
  status reads `2 bookmarks` and the Name/URL text is untouched.
- `acceptance_clear_filter_command_is_registered_with_ctrl_l`: reads
  `Runtime::commands_for` and finds exactly one "Clear filter" command:
  Application scope, shortcut `[KeyChord::primary('l')]`, enabled.
- `acceptance_typed_add_appends_trims_and_clears`: a refused add, then a
  successful add with character-typed input, checking append/trim/fields
  cleared/error cleared/status.

All three pass against the unchanged application (evidence/06). Ctrl+L is
exercised on Linux only. `KeyChord::primary` maps to Cmd on macOS, but that
mapping is not natively evidenced here.
