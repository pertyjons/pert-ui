## Merged findings

1. **No recipe for the editable list** (r1-2-claude#2, pilot-2-claude#2, the first
   of r1-2-claude's "three changes" and the second of pilot-2-claude's). One guide
   section is the fix, and it should also cover findings 2, 4 and 5.
2. **Per-row state in a list** (r1-2-claude#4, pilot-2-claude#3; both closing
   "three changes"; the inventory example's `ActiveCell` is the library's own
   instance). Controls bind only `Signal`s and `ListItems::build`/`TableItems::cell`
   have no state owner. The `sibling` workaround discards open drafts on every
   source change. This is application evidence for the "Controlled controls"
   follow-up.
3. **No programmatic start for `InlineText`** (r1-2-claude#5, pilot-2-claude#7,
   pilot-2-claude#9; both closing "three changes"). Two testers independently
   synthesized F2/Enter, and one ran into held-key classification. This is
   application evidence for the "Sessions for more editors" follow-up.
   r1-2-codex and pilot-2-codex avoided the gap with a custom `DraftEditor` owner,
   which led them to merged finding 6.
4. **Hidden selection under a filter** (r1-2-claude#8, r1-2-codex#3, and the
   trimming note). All four task-2 submissions write their own "is the selected
   task shown" logic. One got it subtly wrong because the trimming is undocumented
   (r1-2-claude); one wrote a `SelectionGuard` component (r1-2-codex); the pilots
   wrote `selected_visible` and their own visibility function.
5. **`InlineText` swallows the row press** (pilot-2-claude#6). It belongs with
   finding 3: both concern `InlineText` as a list-row editor.
6. **`DraftEditor` owners inside redescribed rows** (r1-2-codex#4, pilot-2-codex#4,
   pilot-2-codex#5/#6). The owner contract covers a single mount, not a parent that
   describes the owner again, and not the owner's `cancel_input` at `begin`.
7. **Editors claim modified arrows ahead of commands** (r1-2-claude#3, the third of
   r1-2-claude's "three changes"). The key list is undocumented, and no scope
   precedes the text phase.

## Library problems found while verifying (not reported by any tester)

- **(unreported) `CollectionFilter` address collision with a collection keyed
  `filter`.** The page states that "`filter` is valid for the collection"
  (rt/collection_filter.rs:421-423), and the collection-key test only checks that
  mounting succeeds (pert-ui/tests/collections/collection_filter.rs:769-791).
  Because the field's wrapper is structural (rt/collection_filter.rs:584), the
  field and such a collection share one address. Probe: with the collection keyed
  `filter`, `find(&root, &["search","filter"])` returns `Err(AmbiguousKey)`, and
  inspection reports the same path `["todo","search","filter"]` for the `List` and
  the `SearchInput`. Tooling selectors and `find` cannot address either. Fix:
  give the wrapper `.slot("filter-field")` so the field's address is
  `…/filter-field/filter` (as the docs already suggest; this changes the
  addresses pilot-2-claude#8 found, so check workspace persistence), or document
  `filter` as reserved too. Destination: TODO.md. Rule: the `find`/`Selector::path`
  addressing contract (rt/runtime/tree.rs:278-296), which treats an address
  shared by two elements as ambiguous; here the library's own wrapper creates
  that ambiguity under a key its docs call valid.
- **(unreported) Text editors claim Alt/Super + Up/Down as plain line movement
  off macOS** (rt/text_fields.rs:1078-1104, :3179). In a single-line `TextField`
  these chords have no editing meaning, yet they hide application shortcuts. This
  is part of merged finding 7, recorded separately because it is a behavior
  change rather than documentation. Destination: TODO.md.
- **(unreported) `FilterOutcome::nearest_active` is not reachable through
  `CollectionFilter`**, the usual way to filter. An application that wants to
  relocate a hidden selection has to recompute what the filter already computed
  (rt/collection_filter.rs:109-122, :438-443). Belongs with r1-2-codex#3's
  follow-up.
- **(unreported, context) Existing follow-ups already cover two of the requests.**
  plans/follow-ups.md:47-53 ("Sessions for more editors", `InlineText`) and
  :54-56 ("Controlled controls"). The friction entries above are the application
  evidence those entries wait for; update them rather than adding new ones.
- TODO.md (76 lines) has no entry touching `InlineText`, `CollectionFilter`,
  `ListFilter`, `DraftEditor` or `Signal::sibling`. Nothing to merge there.
