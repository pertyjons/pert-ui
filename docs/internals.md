# Implementation notes

This document is for maintainers. It records the implementation rationale and
internal ordering behind some rules of the
[state, composition and interaction contracts](contracts.md). Every guarantee
an application, a custom component or a custom host relies on is stated in
contracts.md; what is here explains how the runtime keeps those guarantees
and may change with the implementation. When a detail here becomes something
others rely on, state it in contracts.md instead.

## Surface admission and command queries

These notes belong to [menus, pickers and
dialogs](contracts.md#menus-pickers-and-dialogs).

Error recovery records the current kind and retries incomplete admission. No-flush
command queries inspect current root visibility and declared kind rather than
cached admission kind, including local Dialog/ViewDialog scope and default
application-command restrictions.

Command queries see newly shown roots that are missing from the last synchronized
frontier. A command listing shares one pass over all mounted nodes across all rows.
Command invocation and native key routing, after flushing all presentation roots
before admission, inspect the synchronized surface frontier without repeating the
full declaration walk.

## Notification delivery

These notes belong to [delivery order and hidden
windows](contracts.md#delivery-order-and-hidden-windows).

Preparation follows the mounted incarnation's current owner and repeats visible
presentation settlement after callback writes, without replaying mailbox, task
or timer delivery frontiers.

Notification followups share the update-wave budget. An exhausted notification
budget is not restarted for pending reveals; ordinary queued reveals use their
normal flush budgets, so independent requests and path depth do not count as
feedback.

ToolWindows associates each reported change with its own delivery slot,
separate from housekeeping, so interleaved layout changes retain request order.
Detached-panel
housekeeping requests coalesce while one wakeup is pending, including hidden roots.

## Failure provenance and input cleanup

These notes belong to [failures and input
cleanup](contracts.md#failures-and-input-cleanup).

Input cancellation applies to direct dispatch errors and failures of notification
requests attributable to that dispatch. The first reported error retains
precedence, but any encountered attributable failure still requires cleanup, even
when an older unrelated error is reported. Older requests, their descendants, and
requests generated by external/preflush work retain their own provenance; their
errors propagate without cancelling another event's focus, capture or drag.
Older/external notification failures during the native-key preflush retain
their separate preservation policy.

Collective presentation-settlement errors without a uniquely attributable request
also propagate without cancelling the current gesture after dispatch. Headless
key failure cleanup follows every mounted incarnation actually called, including
keyboard and Escape-text bubbling, even if preparation or callbacks transfer
focus. Completed focus-loss, focusability-loss, hiding and surface-admission
capture cancellation is not repeated by later failure cleanup. Transfers into an
owner's subtree preserve its existing context policy. With no dispatched callback,
preparation failure cleanup retains the preflush owner. Regaining focus or
receiving keyboard, text, IME, text-command or general event input starts a fresh
input context.

Later focusability loss still clears focus after an already completed cancellation.
If a preflush blocks a held key's release or the last held pointer button's release
before its owner receives it, cleanup still ends the held action or edit. Pending
requests hold weak input provenance and cannot retarget a later event. Nested
input calls share request lineage but scope error classification to their own call.

Queued reveals preserve their request's weak provenance while invoking container
reveal hooks, and parameter delivery runs without current-input provenance.

## Runtime shutdown

These notes belong to [runtime shutdown](contracts.md#runtime-shutdown).

Outside shutdown, retirement appends queued cleanup causes to a surviving window
rather than discarding them. Terminal OwnerRemoved failures are queued
individually and do not retry the removed owner; an earlier coalesced
surface-dismissal cause remains observable. Within a window,
focus/terminal-removal errors keep FIFO order before that stored surface cause.
A visible surviving window stays due until delivery.
